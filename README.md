# Распределённый анализ вакансий DevOps в RustFS

Лабораторная работа для индивидуального варианта 11 «DevOps инженер».
Собственная MapReduce-реализация читает NDJSON из RustFS чанками через S3 Range
GET и считает частоты отдельных навыков, пар и троек. Независимый SQL в DuckDB
обращается к тому же S3-объекту через `httpfs`. Результаты сверяются полностью.

## Как устроен расчёт

Подготовка оставляет вакансии DevOps/SRE/Platform Engineer и записывает NDJSON:
одна вакансия на строку, навыки нормализованы, отсортированы и не повторяются.
MapReduce разбивает S3-объект на байтовые диапазоны. Каждый Mapper читает свой
диапазон через Range GET и считает навыки, пары и тройки. Reducer объединяет
результаты и записывает три JSON-документа с одинаковым порядком сортировки.
DuckDB независимо считает те же комбинации SQL-запросами.

В `baseline` Mapper передаёт списки всех комбинаций, в `optimized` локальный
combiner передаёт счётчики. Reducer одинаков для обоих режимов. Формат итоговых
JSON сохранён, поэтому результат можно сверять целиком и сравнивать с исходными
контрольными суммами.

## Структура

- `src/prepare_dataset.py` - фильтр варианта, нормализация и NDJSON;
- `src/s3_io.py` - создание бакета, загрузка и инвентаризация;
- `src/mapreduce_s3.py` - собственный MapReduce по S3 Range GET;
- `src/duckdb_counts_s3.py` - сопоставимый SQL-подсчёт в DuckDB;
- `src/duckdb_analysis.py` - зарплаты и регионы;
- `src/verify_results.py` - полное сравнение результатов;
- `src/profile_pipeline.py` - запуск методов и измерение времени и памяти;
- `tests/` - регрессионные тесты и воспроизводимый локальный эксперимент;
- `evidence/` - журналы запусков и скриншоты RustFS;
- `report/` - исходный PDF-отчёт.

## Подготовка

Исходный файл `it_vacancies_2024.csv` объёмом 847 619 384 байта не включён в
репозиторий. Его SHA-256:
`303db922b541e4440906f5a7e8be32fb55e8808f950ffddb8c272f1548212a65`.
Файл нужно положить рядом с каталогом проекта либо скорректировать путь в
команде подготовки.

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt
Copy-Item .env.example .env
```

Значения `RUSTFS_ACCESS_KEY` и `RUSTFS_SECRET_KEY` задаются локально и не
фиксируются в Git. Для нового стенда можно использовать четыре каталога из
`docker-compose.yml`:

```powershell
docker compose --env-file .env up -d
$env:RUSTFS_ACCESS_KEY = "<access-key>"
$env:RUSTFS_SECRET_KEY = "<secret-key>"
$env:RUSTFS_ENDPOINT = "http://127.0.0.1:9000"
$env:RUSTFS_BUCKET = "hh-lake"
python -c "import duckdb; duckdb.connect().execute('INSTALL httpfs')"
```

## Воспроизведение

```powershell
python src/prepare_dataset.py ..\it_vacancies_2024.csv --out-dir data/prepared
python src/s3_io.py upload ..\it_vacancies_2024.csv raw/it_vacancies_2024.csv
python src/s3_io.py upload data/prepared/devops_vacancies.ndjson variants/devops/vacancies.ndjson
python src/mapreduce_s3.py --out-dir results/mapreduce --mode optimized --workers 4 --chunk-bytes 524288
python src/duckdb_counts_s3.py --out-dir results/duckdb_counts_only --threads 4
python src/duckdb_analysis.py --out-dir results/duckdb --threads 4
python src/duckdb_variant_check.py --out evidence/duckdb_variant_check.json
python src/verify_results.py results/mapreduce results/duckdb_counts_only --out evidence/verification.json
python src/profile_pipeline.py --attempts 3 --out evidence/profiling.json
```

Для теста retry используется тот же входной объект; ошибка внедряется только в
первую попытку второго чанка:

```powershell
python src/mapreduce_s3.py --out-dir results/failure-test --mode optimized --inject-failure
```


## Проверки без RustFS

Для этих команд достаточно зависимостей из `requirements.txt`; ключи S3 не нужны:

```powershell
python -X utf8 -m unittest discover -s tests -v
python -X utf8 tests/run_experiments.py --attempts 3
```

Тесты проверяют границы чанков, UTF-8/CRLF, отсутствие последнего перевода строки,
запись размером 200 КБ, отсутствие потерь и дублей, эквивалентность режимов,
ошибочный JSON, лимит повторов и восстановление после отказа Mapper.

Локальный эксперимент использует полный подготовленный датасет и HTTP-стенд с
HEAD/Range GET. Для 1, 2, 4 процессов с чанком 1 МиБ и для 4 процессов с чанком
256 КиБ он запускает оба режима, измеряет время и память, сверяет каждый результат
с SQL DuckDB и проверяет искусственный отказ. DuckDB читает локальный файл.
Условия и фактические цифры находятся в
[evidence/experiment_notes.md](evidence/experiment_notes.md), сырые измерения — в
[evidence/local_experiments.json](evidence/local_experiments.json).

## Особенности реализации и ограничения

`ProcessPoolExecutor` позволяет распределить Python-подсчёт между процессами.
Для небольшого файла затраты на создание процессов, сериализацию и запись JSON
могут перевесить экономию combiner. Число процессов само по себе не увеличивает
число задач: при файле 1,88 МБ и чанке 1 МиБ их всего две.

Запись принадлежит чанку, содержащему её первый байт. Если чанк начинается внутри
строки, её хвост пропускается; если заканчивается внутри строки, Mapper дочитывает
её блоками по 64 КиБ. Перевод строки на самой границе уже завершает запись.
Фиксированного ограничения в 64 КиБ больше нет. При этом память Mapper должна
вмещать диапазон и дочитанную запись. Для очень длинной строки соседние чанки
повторно читают её хвост; это корректно, но увеличивает объём запросов.

В памяти комбинации представлены кортежами, в JSON — списками. Это исключает
служебный строковый разделитель из ключей. Подготовленный набор содержит
уникальные `vacancy_id` и уникальные навыки в каждой вакансии; SQL-соединения
предполагают эту уникальность. Входной S3-объект во время расчёта менять нельзя.

Повторяется только задача с временной сетевой ошибкой, HTTP 408/429/5xx,
S3 SlowDown/RequestTimeout или контролируемым тестовым отказом. Ошибки JSON,
структуры навыков, доступа и отсутствующий объект завершают расчёт. Журнал
содержит номер чанка, диапазон байтов, попытку и причину. `--max-retries` задаёт
число дополнительных попыток задачи; внутренние повторы boto3 идут отдельно.
Искусственный отказ возникает в первой попытке второго чанка, поэтому для
проверки нужны как минимум два чанка. Падение самого процесса не восстанавливается:
сломанный пул требует перезапуска расчёта.

Метрика `intermediate_items` показывает число переданных комбинаций или ключей
счётчика. `intermediate_pickle_bytes` — сумма размеров сериализованных payload
успешных задач, без обрамления IPC. Для измерения выполняется дополнительная
сериализация, её затраты входят во время. Пик RSS — максимум суммы памяти дерева
процессов при опросе каждые 10 мс; общие страницы могут учитываться несколько раз.
Это оценка, а не точный размер физической памяти.

## Результаты и воспроизводимость

Исходные журналы RustFS находятся в `evidence/`; они не являются новыми замерами
после рефакторинга. В исходном расчёте отобрано 6 215 из 229 388 вакансий,
получено 1 541 навык, 25 462 пары и 195 366 троек. Новые локальные проверки сверяют
все документы с DuckDB и с контрольными суммами исходного результата.

Зарплатный и региональный анализ сохранён в `duckdb_analysis.py`: 1 364 вакансии
с сопоставимыми RUR-значениями, Москва, Санкт-Петербург и Екатеринбург. Исходный
CSV не включён в репозиторий, поэтому его фильтрация и анализ исходных данных
требуют отдельного файла. Полный повтор работы с RustFS выполняется командами
раздела «Воспроизведение» при доступном стенде; локальные результаты не измеряют
производительность RustFS или DuckDB httpfs.
